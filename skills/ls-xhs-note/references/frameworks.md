# Frameworks

> Framework gives the note a usable body.  
> Insight gives the note a reason to exist.  
> Platform adaptation decides whether the note feels native or forced.

---

## Quick Selection Matrix

| Signal | Framework | Why it fits | Danger zone |
|--------|-----------|-------------|-------------|
| One repeated frustration blocks progress | Pain-Point | Strong recognition and strong save intent | Turns into empty empathy if the cost is vague |
| One turning point reveals a transferable lesson | Story | Strong completion and authority | Becomes slow if background takes over |
| Multiple useful takeaways are stronger in sequence | Listicle | Best for scan speed and saves | Feels thin if points do not escalate |
| Two choices produce real trade-offs | Comparison | Good for comments and decision support | Collapses if the answer is obvious from the start |
| One event hides a deeper judgment | Judgment Breakdown | Best for opinion plus explanation | Sounds like generic commentary without a deep layer |
| One method or system must become usable fast | Technical Breakdown | Best for turning complexity into action | Reads like product docs if no judgment is present |
| Uncertain | Pain-Point | Most forgiving and easiest to convert into native note rhythm | — |

## Adaptation rule

Keep the original reasoning structure.  
Rewrite the presentation for native note reading:

- lead with tension, not setup
- put the actionable or judgment-heavy line in the first screen
- use shorter paragraphs and sharper scan breaks
- keep each section visually sliceable for card generation
- reduce background until only the useful layer remains

## Viral note overlay

Framework decides the logic. Viral note packaging decides the reading speed.

Apply the same overlay to every framework:

- first screen must carry a mistake, a cost, a contrast, or a result
- lines should feel scroll-native, not article-native
- every body move should increase save value, not only completeness
- one light emoji anchor is allowed when it improves scan speed
- comments should be invited through a real choice or bottleneck, not through empty engagement bait

Useful opening moves:

- `Most people think X. The real issue is Y.`
- `If the result keeps failing, the bottleneck is usually not where people look first.`
- `The visible comparison is weak. The useful comparison starts one layer deeper.`
- `I would not start from the feature list. I would start from the handoff cost.`

## 1. Pain-Point

**Best for:** one visible problem that keeps repeating, especially when people are fixing the wrong layer  
**Promise:** the note helps the reader see the real blockage and the first useful fix  
**Reading arc:** recognition -> reframing -> immediate action -> relief

### Native note version

- open with the lived cost, not a general topic intro
- name the wrong assumption quickly
- move to the real bottleneck in the first screen
- keep the fix practical and near-term
- package the middle with a visible before/after or wrong/right contrast
- let the ending land on what stops repeating after the fix

### Working shape

1. recognition line
2. what people usually misread
3. what the real problem is
4. what to change first
5. what improves after the change

### Danger zone

- empathy without a diagnosis
- background before the pain becomes visible
- advice that sounds abstract or motivational

### High-performing packaging tendency

- good lead: `You do not keep losing time because you move slowly. You keep losing time because the same layer breaks every round.`
- strong middle: wrong fix -> real blockage -> first correction
- strong close: ask which repeated cost hurts most now

## 2. Story

**Best for:** one turning point, one decision, one before-and-after shift  
**Promise:** the note turns a narrative moment into a reusable lesson  
**Reading arc:** curiosity -> tension -> turn -> insight -> reuse

### Native note version

- compress the background hard
- use one sharp scene or decision point
- extract one transferable judgment instead of replaying the whole story
- end with how to apply the lesson, not how the story felt
- keep the emotional swing, but translate it into a decision rule
- make the turn happen before the reader has to commit to a long setup

### Working shape

1. hook with the turning point
2. minimum context for stakes
3. what changed
4. why the change mattered
5. how to use the lesson

### Danger zone

- long warmup paragraphs
- story value with no reusable takeaway
- emotional description without a clear decision

### High-performing packaging tendency

- good lead: the turn comes first, the context comes second
- strong middle: one failed assumption -> one changed move -> one reusable rule
- strong close: ask where the reader is still using the old move

## 3. Listicle

**Best for:** multiple lessons, methods, mistakes, or principles that become stronger when scanned together  
**Promise:** the note gives a save-worthy bundle of direct takeaways  
**Reading arc:** promise -> quick payoff -> rising value -> one compressed rule

### Native note version

- keep the list tight
- make every point distinct
- prefer three strong points over a padded number
- let each point answer "why it matters now"
- make the list feel save-worthy in the first three lines
- use progression: quick win -> deeper layer -> decision rule

### Working shape

1. opening promise
2. one-line conclusion
3. point one
4. point two
5. point three or more
6. one rule to remember

### Danger zone

- filler points added for symmetry
- points that repeat the same idea with new nouns
- list items that label a topic but never explain the consequence

### High-performing packaging tendency

- good lead: promise a usable bundle, not a vague collection
- strong middle: each point should carry a consequence or shortcut
- strong close: compress the whole list into one rule the reader can reuse later

## 4. Comparison

**Best for:** real choices with meaningful trade-offs  
**Promise:** the note helps the reader pick the right path faster  
**Reading arc:** dilemma -> selection criteria -> side-by-side contrast -> recommendation

### Native note version

- state the actual decision in one line
- reframe the decision if the surface question is weak
- compare through consequences, not feature inventory
- tell the reader who each option is for
- package the comparison as a judgment switch, not a neutral checklist
- use contrast language early: `people compare X, but should compare Y`

### Working shape

1. the decision people are trying to make
2. what actually matters in the comparison
3. option A
4. option B
5. recommendation by audience fit

### Danger zone

- pretending both sides are viable when one side clearly is not
- comparison by abstract pros and cons
- no audience-fit answer at the end

### High-performing packaging tendency

- good lead: visible question -> hidden comparison rule
- strong middle: A fails here / B fails there / the real deciding layer is deeper
- strong close: tell the reader who should choose what and why

## 5. Judgment Breakdown

**Best for:** a visible event, trend, or update that hides a deeper implication  
**Promise:** the note turns surface noise into durable judgment  
**Reading arc:** surface event -> hidden layer -> mechanism -> consequence

### Native note version

- start from the visible signal
- move quickly to the hidden layer
- explain why the signal matters, not only what happened
- keep one core judgment at the center
- frame the note as a sharper read, not a louder opinion
- use one contradiction line early so the hidden layer arrives fast

### Working shape

1. visible trigger
2. why surface interpretation is weak
3. deeper judgment
4. mechanism or pattern
5. what changes if the judgment is right

### Danger zone

- hot take wording with no mechanism
- repeating news without adding structure
- trying to carry multiple judgments at once

### High-performing packaging tendency

- good lead: `The update is visible. The useful signal is somewhere else.`
- strong middle: surface reading -> weak reading -> deeper mechanism
- strong close: ask which future move changes if the judgment is correct

## 6. Technical Breakdown

**Best for:** systems, workflows, methods, or tools that need a fast usable explanation  
**Promise:** the note makes a complex method clear enough to use today  
**Reading arc:** confusion -> simplification -> steps or layers -> result

### Native note version

- strip theory to the minimum needed for action
- put the practical sequence before deep explanation
- use one clear internal model
- keep terms concrete and reusable
- make the note feel like a shortcut, not a mini manual
- use fast labels, checks, and failure cues to preserve reading speed

### Working shape

1. what usually feels confusing
2. the simplified model
3. the key steps or layers
4. the most common failure mode
5. what good execution looks like

### Danger zone

- tutorial language with no judgment
- too much architecture before the first usable step
- definitions that read like documentation

### High-performing packaging tendency

- good lead: `If the workflow still feels messy, the missing piece is usually one model, not more tools.`
- strong middle: model -> 2-4 usable moves -> common failure check
- strong close: ask which part readers want expanded next

## Selection defaults

- choose `Pain-Point` when a repeated problem is the real entry point
- choose `Story` when a turning point carries the lesson better than a thesis statement
- choose `Listicle` when the note truly depends on multiple save-worthy points
- choose `Comparison` when the reader needs to choose, not just understand
- choose `Judgment Breakdown` when one event hides a deeper implication
- choose `Technical Breakdown` when a system needs simplification more than opinion
